# Rust Language Pack Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Svarupa analyzes Rust the way it analyzes Go and C#: symbols, `use` and `mod` imports, calls, crate module resolution through `Cargo.toml`, function metrics, security and runtime risk facts, plain explanations with Rust examples, health and design that count Rust, and benchmark facts.

**Architecture:** A new data pack `svarupa/extract/packs/rust.py`, built by mirroring `svarupa/extract/packs/go.py`. Go is the closest model because its methods are also declared outside the type (`func (s *T) M()` is like `impl T { fn m(&self) }`), and its imports resolve through a manifest (`go.mod` is like `Cargo.toml`). Add a `RustCrates` resolver next to `GoModules` in `svarupa/extract/packs/modules.py`, plus RiskSpec data and `rust` examples in the explanation TOML files. Design units must know `Cargo.toml`, and there is a benchmark corpus entry. The walker and the health engine stay language-neutral.

**Tech Stack:** Python 3.10+, `tree-sitter-rust==0.24.2` (pinned, per the language-packs spec), pytest.

**Spec:** `docs/superpowers/specs/2026-10-03-language-packs-design.md`. The Rust row is `tree-sitter-rust` 0.24.2, and the resolver kind is `module-file`, which reads `Cargo.toml`. Health behavior follows `2026-10-10-security-scaling-1c3-design.md` and `2026-10-24-plain-explanations-1c4-design.md`.

## Global Constraints

- The pack is data plus the few hooks data cannot express. The walker never names a language.
- Any new shared field must default to the old behavior, and the other six packs' facts must not change.
- Use the shared options the C# pack added before inventing new ones: `RiskSpec.async_holder`, `RiskSpec.arg_wrapper`, `MetricsSpec.is_function`, `MetricsSpec.name_of`, the `LAST_NAMED` sentinel, and `FileFacts.namespaces`.
- The new maturity is whatever `test_pack_maturity_follows_the_benchmark` demands.
- Evidence for every fact is the node's own line, and facts come out in document order.
- No literal from source reaches a risk fact's detail.
- `std`, `core` and `alloc` are external, as is every dependency in any `Cargo.toml` (`[dependencies]`, `[dev-dependencies]`, `[build-dependencies]`, `[workspace.dependencies]`). A crate name's `-` becomes `_`. A crate the repo itself declares is never external.
- Rust has no `catch`, so swallowed-error gets no Rust rule and no Rust example.
- Routes are not extracted for Rust, the same as Go. So there are no auth markers and no endpoint-without-auth example.
- Health and design must count Rust. The `_CODE` set in `svarupa/health/__init__.py` is now built from the packs, so check that `rust` appears in it. `svarupa/design/units.py` must treat `.rs` as code and `Cargo.toml` as a unit manifest.
- This branch must pass its own gate: `uv run svarupa check . --base main` exits 0. The full suite is green at the end of every task except where a ledger ruling says otherwise.
- Plain English, no em dashes. Commits are SSH-signed (repo-local config), use the imperative mood, stay under 72 characters, and carry no AI attribution.

## Node types (probed from tree-sitter-rust 0.24.2)

- Files and modules:
  - `source_file`.
  - `use_declaration` has field `argument`: one of `scoped_identifier` (`path`, `name`), `scoped_use_list` (`path`, then a `use_list` of `identifier`/`use_as_clause`/nested lists), `use_as_clause`, `use_wildcard`, or `identifier`. Path roots can be `crate`, `self`, `super`, or a crate name.
  - `mod_item` has field `name`. With field `body` (`declaration_list`) it is an inline module. Without a body, `mod x;` names a child module file.
- Types:
  - `struct_item`, `enum_item` and `union_item` (fields `name`, `body`) are kind class.
  - `trait_item` (fields `name`, `body: declaration_list`, holding `function_signature_item` or `function_item`) is kind interface.
  - `type_item` is an alias.
- Impl blocks: `impl_item` has fields `type`, `trait` (optional) and `body: declaration_list`. Methods are the `function_item`s inside it.
  - `impl Trait for Type` makes `Trait` a base of `Type` for call resolution.
  - The impl can be in a different file from the struct. Mirror how go.py attaches receiver methods to their type.
- Functions:
  - `function_item` has fields `name`, `parameters` (may include `self_parameter`), `body: block`.
  - `function_modifiers` holds `async`, `unsafe` and `const`; this is the async holder.
  - `closure_expression` is a nested function.
- Attributes: `attribute_item` > `attribute` holds an `identifier` and optional `arguments: token_tree`. These become decorators (`#[derive(Debug)]`, `#[tokio::main]`, `#[get("/x")]`).
- Calls: `call_expression` has fields `function` and `arguments`. `function` is one of:
  - `identifier`: bare.
  - `scoped_identifier`: `Type::new` or `module::f`, qualified on the path.
  - `field_expression` with fields `value` and `field`: a method call `x.f()`, with `self.f()` as SELF.
  - `generic_function`.
- `macro_invocation` has field `macro`. It is NOT a call fact, except where a risk rule needs it (`format!` builds a string).
- Branches: `if_expression` (an else-if is an `if_expression` inside `else_clause`), `match_expression` with `match_arm`s (a wildcard `_` arm is the default), `while_expression`, `loop_expression`, `for_expression`, `binary_expression` with `&&`/`||`, `let_condition`, and `try_expression` (`?`).

## Review Focus

1. A method in `impl Shop { fn save(&self) }` in another file than `struct Shop` is `Shop.save`, and `self.save()` and `shop.save()` (with `shop: Shop` as a field) resolve to it. Pinned in Task 1 and Task 2.
2. `use crate::db::Repo;` resolves to `src/db.rs` or `src/db/mod.rs`. `use super::x` and `use self::x` resolve relative to the file's module. `use std::...` and `use serde::...` (a Cargo dependency) are external, never dangling. Pinned in Task 2.
3. A workspace with two crates: `use shop_core::Order` in crate `shop_api` resolves to the other crate's file when `shop-core` is a workspace member. Pinned in Task 2.
4. `async fn` is async (the `async` sits under `function_modifiers`). `std::thread::sleep` in an async fn fires blocking-in-async. `tokio::time::sleep(..).await` does not. Pinned in Task 4.
5. `sqlx::query(&format!("... {}", id))` is SQL injection, while `sqlx::query("... $1").bind(id)` and the `sqlx::query!` macro are not. Pinned in Task 4.

**Interfaces:**
- Produces `rust.PACK` with `lang="rust"`.
- Rules:
  - `use_declaration` becomes an Import. The specifier is the full path joined with `::` and written as dotted (`crate.db.Repo`). Each braced list item gives its own name, and `as` gives `alias_of`.
  - `mod_item` without a body is an Import of `self.<name>`. With a body, it is a Custom that qualifies the inner items by the module name.
  - The type items become Define rules.
  - `impl_item` is a Custom that sets the owning type (and the trait base) for its functions.
  - `function_item` is a Define (a method inside an impl or trait, a function otherwise).
  - `call_expression` is a Call.
  - `attribute_item` becomes decorators on the next item.
- `qualified_prefix`: the module path from the crate root. `src/lib.rs` and `src/main.rs` are the root, `src/a/b.rs` is `a.b`, and `src/a/mod.rs` is `a`. Prefix the crate name when the file is in a workspace member.

### Task 2: Crate module resolution

**Files:** `svarupa/extract/packs/modules.py` (new `RustCrates`, mirroring `GoModules`), `rust.py` (`modules=RustCrates`), `svarupa/extract/__init__.py` (Cargo dependencies into the declared deps, mirroring how `go.mod` requires are read), `tests/test_module_resolvers.py`, a `tests/golden_repos/rust_shop.json` fixture repo, and `tests/test_golden_repos.py`.

**Interfaces:** `RustCrates(context)` reads every `Cargo.toml` (`[package] name`, `[workspace] members` including globs, and the dependency tables) with `tomllib`/`tomli`.

`targets(spec, from_file)`:
- Resolves `crate.a.b[.Item]` to the longest prefix that is a module file of the caller's crate: `a/b.rs`, `a/b/mod.rs`, or an inline module in a parent file.
- Resolves `self.x` relative to the caller's module and `super.x` relative to its parent.
- Resolves `<member_crate>.a.b` into that member's crate.

`is_external(spec)`:
- True for `std`, `core` and `alloc`.
- True for any Cargo dependency (with `-` changed to `_`).
- False for workspace members.

Tune `fields_without_this` and `package_scoped_bare` like Go:
- Bare calls resolve within the same module file and its `use` names.
- Field calls go through `self.field`.

- [ ] Tests first:
  - `crate.db` resolves to `db.rs`, and also to `db/mod.rs`.
  - `crate.db.Repo` resolves to `db.rs`.
  - `super.x` and `self.x` resolve relative to the file's module.
  - `mod handlers;` resolves to `handlers.rs` and to `handlers/mod.rs`.
  - A workspace member crate import resolves into the other crate.
  - `std.fmt` and a Cargo dependency are external. A crate nobody declares is unresolved, never invented.
  - In the golden repo (a two-crate workspace, `api` using `core`), the module dependency goes api -> core, and a method call through a struct field resolves to the impl method.

### Task 4: Security and runtime risks

**Files:** `rust.py` (`risk_callee`, `RISKS`), `tests/test_risks.py`. Each rule gets a true case and a safe twin as separately named tests.

Rules (data; mirror the C# and Go `RISKS` shape):
- **String building:** `format!` macro invocations with arguments, `+` on strings, and `String::push_str` are built. A string literal and `concat!` of literals are not.
- **Sinks:**
  - **sql:** `(?:^|::|\.)(?:query|query_as|query_scalar)$` on an `sqlx` path or receiver, `sql_query$` (diesel), and `(?:^|\.)(?:execute|query|query_row|prepare|batch_execute)$` on receivers named like a connection or client (`conn`, `connection`, `client`, `tx`, `db`, `pool`, `\w*_conn`). The rule fires only when the SQL argument is built. The `sqlx::query!` and `query_as!` macros are compile-time checked and never fire.
  - **shell:** `Command::new` when its program argument is built, or when a later `.arg(...)` in the same chain is built and the program is `sh`, `bash` or `cmd`.
- **Unsafe settings:**
  - **tls-verify-off:** `danger_accept_invalid_certs\(\s*true` and `danger_accept_invalid_hostnames\(\s*true`.
  - **weak-hash:** `md5::compute\(`, `Md5::new\(`, `Sha1::new\(`, and `sha1::Sha1`.
  - **cors-any-origin:** `CorsLayer::permissive\(`, `CorsLayer::very_permissive\(`, `allow_origin\(\s*(?:Any|AllowOrigin::any\(\))`, `Cors::permissive\(`, and `allow_any_origin\(`.
  - **unsafe-deserialize:** no Rust rule, since serde is not a gadget-chain risk. Ruling.
- **Runtime:**
  - Loops are `for_expression`, `while_expression` and `loop_expression`. Loop callees are `\.(?:for_each|map|try_for_each)$`.
  - Datastore calls are `fetch_one|fetch_all|fetch_optional|fetch|execute|load|get_result|get_results|first|query_row` on an sqlx/diesel shape.
  - The async marker is `async` under `function_modifiers`, using `async_holder`.
  - Blocking-in-async covers `(?:std::)?thread::sleep$`, `(?:std::)?fs::(?:read|read_to_string|write|read_dir|copy|remove_file)$`, `\.blocking_(?:send|recv|lock|read|write)$`, and `reqwest::blocking::`.
  - No catch rule.

- [ ] Tests first, covering Review Focus items 4 and 5 and every rule's twin. Add these safe twins:
  - `tokio::fs::read_to_string(..).await` in async does not fire.
  - `thread::sleep` in a non-async fn does not fire.
  - A literal-only `sqlx::query("select 1")` does not fire.
  - `.bind(id)` does not fire.
- [ ] Commit "Add Rust sinks, unsafe settings and runtime risks".
